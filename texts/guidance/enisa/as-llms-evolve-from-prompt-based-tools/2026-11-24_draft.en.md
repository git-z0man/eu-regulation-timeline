Organisations are migrating AI agents from experimentation into business processes to production environments where cybersecurity is most needed. This report is aimed towards the experts that are going to be involved in those deployment decisions with an aim at highlighting where cybersecurity risks and security weaknesses can emerge across the seven steps of the Agentic AI Cyber Security Implementation Roadmap. From defining the purpose of an AI agent to decommissioning it, cyber security teams should be able to verify that an agent is allowed to act with organisational data, identities, tools and infrastructure in a secure way.

This report directly supports Key Action 4 of the EU Action Plan on Cybersecurity and Artificial Intelligence (7 July 2026), under which ENISA, in cooperation with relevant Union entities, is to issue guidance, recommendations, advisories and best practices on protection against AI-powered threats and on the secure integration of AI in cybersecurity operations. This report contributes to that objective by helping organisations apply cybersecurity fundamentals and preparedness to AI-agent deployment and understanding where risks can arise.

The report serves CISOs and risk owners making deployment decisions, security architects and engineering teams implementing controls, and compliance teams assessing obligations, including the EU AI Act where applicable. Decisionmakers can use the seven-step roadmap to set approval gates while technical teams can use the risk area catalogue as a technical reference and Annex B checklist to collect evidence.

Finally, a relevant AI skill has been developed and accompanies this report, guiding organisations through the Cybersecurity Agentic AI deployment readiness checklist (Annex B), helping teams evaluate their risk capture evidence, identify gaps and turn findings into an actionable deployment review.

This report therefore aims to create informed organisational awareness before deployment and to support repeatable security decisions during deployment of AI agents especially in cybersecurity operations. It does not replace applicable legal obligations, sector requirements or established cybersecurity controls but helps organisations apply those fundamentals to the specific behaviours and risk surfaces of AI agents.

## 1. Introduction

For this report, the term AI agent refers to an AI system, or coordinated set of AI systems, that can pursue a goal through a sequence of decisions and actions with a degree of autonomy, using one or more AI models together with tools, data, memory or external services. The term agentic AI refers to the broader system behaviour and architecture through which such autonomy is enabled, including reasoning, orchestration, memory, tool use, delegation and interaction with external systems. Accordingly, the report uses AI agent when referring to the deployed component that performs tasks, and agentic AI when referring to the wider operational set-up in which that component acts.

This distinction matters because the cybersecurity risk does not arise only from the model itself, but from the way autonomy is implemented and connected to organisational systems. An AI agent that only returns text presents a different security profile from an agentic AI deployment in which the agent can send emails, modify infrastructure, query sensitive databases, execute code or instruct another agent. The more authority an organisation delegates to an AI agent within that broader agentic set-up, the more important it becomes to define and enforce the boundaries around that authority.

Deploying an AI agent in this way, whether for routine office work or for specialised cybersecurity operations, like incident response and monitoring, introduces additional security weaknesses because the system can translate model output into operational actions. An AI agent may plan across multiple steps, retain memory, call external tools, delegate tasks and act with limited human intervention. The resulting risk is therefore not limited to incorrect output; model-driven errors, malicious instructions, compromised dependencies or excessive permissions may be converted into operational actions with potentially dangerous consequences.

Why this report now

Organisations are already integrating AI agents into business and cybersecurity workflows, while the broader agentic AI architectures in which those agents operate continue to evolve rapidly alongside standards, products and supervisory practices. This distinction is important for the purpose of this report. The cybersecurity challenge addressed here lies not only in securing the individual AI agent, but in securing the agentic AI deployment environment, including the connections, permissions, dependencies and execution paths through which the agent can act.

This report is therefore intended to help organisations make defensible deployment decisions for AI agents operating within their infrastructure: identify the risk areas that matter, especially where the AI agent is about to be used in a cybersecurity related deployment, apply cybersecurity fundamentals at the right point in the lifecycle, and maintain the ability to observe, constrain and stop the system whenever it is needed after it enters production.

The EU Action Plan on Cybersecurity and Artificial Intelligence ^(1) provides the policy context for this objective. Key Action 4 explicitly calls for ENISA guidance, recommendations, advisories and best practices on protection against AI-powered threats and on the secure integration of AI in cybersecurity operations. This report supports both sides of that mandate by helping organisations strengthen preparedness for an AI-enabled threat landscape, while also securing the deployment of the AI agents which integrate into cybersecurity and other operational workflows.

Who should use this report

Security managers like CISOs and risk owners can use the seven-step roadmap to decide whether deployment should proceed. Security architects and engineering teams can use the risk area catalogue to implement and test controls. Compliance teams can use the checklist alongside applicable requirements, including the EU AI Act where relevant.

Scope and boundaries

The report focuses on cybersecurity risks arising from the deployment and operation of AI agents. Ethics, fairness and general model quality are outside scope unless they directly affect cybersecurity. The catalogue focuses on weaknesses introduced or materially amplified by autonomy, persistent state, tool use, external integrations and delegation under the cybersecurity context.

The risk area categories presented in this report are intended to help organisations connect technical weaknesses to operational risk. They group weaknesses according to where the main risks arise within an agentic AI deployment, such as the runtime environment, the reasoning and orchestration layer, memory and state, tools and integrations, inter-agent interaction, or even identity and oversight. This structure is intended to support the report’s target audience in identifying which parts of agentic AI deployment introduce which types of cybersecurity exposure, and at what stage of the deployment lifecycle those exposures become relevant.

In this way, the report is not only a catalogue of weaknesses, but a decision-support tool. It helps organisations assess how specific weaknesses may translate into risks to confidentiality, integrity or availability depending on the permissions, data access, tools, infrastructure and level of autonomy granted to the deployed AI agent. The categories should therefore be used together with the seven-step deployment roadmap to determine which security risk areas require attention at a given stage, what evidence should be requested before deployment proceeds, and where existing cybersecurity controls may need to be adapted or reinforced for agentic AI.

The underlying research base covers academic research, reputable threat reporting, public standards and frameworks reviewed up to March 2026. In July 2026, the EU Action Plan on Cybersecurity and AI was adopted and is incorporated here as policy context for how organisations should use the findings; it is not treated retroactively as part of the study evidence base. Selected incidents reported later in 2026 are included only where clearly identified as contextual updates. The specific field covered in this report is evolving rapidly and organisations should expect both the threat landscape and available guidance to continue changing.

## 2. Methodology

The risk area catalogue is grounded in a mixed-methods study combining literature review, threat and incident reporting, standards review. This section explains the evidence base. Readers focused on a deployment decision can move directly to the risk area catalogue and return here when they need to understand how findings were derived.

<a id="sec-2-1"></a>
### 2.1 Literature review

The literature review covered peer-reviewed publications and pre-print research in the current year (2026) until the publication of this report, focusing on cybersecurity aspects of AI agents. These publications were identified through targeted queries across general academic databases and subjectspecific repositories, using terms related to agentic AI, AI agents, cybersecurity, orchestration, tool use, memory, delegation and AI security. However, the examined field continues evolving, so later developments will be considered in future publications on the same topic.

The literature was coded around recurring themes like:

- • Weaknesses, AI agents failure modes and risk areas;

- • attack and risk surface;

- • mitigation approaches and control patterns. These themes were used to build and refine the taxonomy presented in the risk area catalogue.

<a id="sec-2-2"></a>
### 2.2 Threat reports & media review

The study reviewed threat reporting from established cybersecurity organisations and publicly reported incidents involving AI-agent workflows. These sources are used to illustrate how specific weaknesses may manifest in practice and are labelled according to the nature of the evidence presented by the source.

Examples are included to make deployment consequences concrete and should be read together with the source classification and evidence limitations stated in each catalogue entry.

<a id="sec-2-3"></a>
### 2.3 Solutions & standards review

Public standards, frameworks and guidance relevant to AI security were reviewed to assess how far they cover the risk areas identified in the study. The purpose was to help organisations reuse established guidance and see where agent-specific behaviour creates gaps or requires additional interpretation.

Recommendations for the risk areas originate either from the reviewed frameworks or from the study assessment. Where guidance is extrapolated beyond its original scope, that should be treated as an implementation interpretation rather than a new normative requirement.

<a id="sec-2-4"></a>
### 2.4 Deriving the severity ratings

The severity labels provide qualitative prioritisation, not a deployment-specific risk score. Figure 2 combines estimated likelihood (horizontal axis) with potential impact (vertical axis). The reviewed evidence informs these judgements but does not establish measured incident probabilities.

Organisations should reassess each rating against their agent’s permissions, data and operational exposure.

Figure 2: Risk matrix

The criticality levels used in this report are:

- • CRITICAL: results in complete compromise of the agent or its operating environment, exploitable with minimal preconditions.

- • HIGH: results in significant impact across confidentiality, integrity or availability, including the loss of proprietary information • MEDIUM: exploitable under specific conditions, with impact contained in scope or severity.

- • LOW: isolated impact, typically requiring unlikely conditions or yielding minimal exposure.

<a id="sec-01"></a>
## 01 · Research, goals & plans

Decide what the AI agent is for, who can invoke it, what authority and autonomy it may have, which systems or actions are out of bounds, which model and external dependencies it relies on, and how it will be monitored.

Primary security risk areas at this stage: improper authentication and broken access control; identity proofing weaknesses; unsafe autonomous decision-making and action planning; insufficient governance, logging and human oversight; and third-party dependency and supply-chain risk.

Decision point for security managers: approves a use case if the organisation can clearly define where the AI agent will operate, what permissions it will hold, which actions are prohibited, which dependencies it relies on, what human or technical oversight applies and who remains accountable for its actions.

<a id="sec-02"></a>
## 02 · Design

Translate the use case into architecture: define interfaces between agents and environments, how tools are sourced and approved, what data and memory are accessible, and how identity, permissions and oversight are enforced across the design.

Primary security risk areas at this stage: broken access control and weak identity design; insufficient governance, logging and monitoring failure; insecure context handling; memory poisoning and unsafe persistent state design; sensitive data disclosure; prompt injection and instruction manipulation; tool metadata poisoning and insecure tool discovery; trust boundary ^(2) weaknesses in multi-agent workflows; and third-party dependency or provider risk.

Decision point for security managers: require the design to define explicit security boundaries for identity, permissions, data, memory, tools, external services and agent-to-agent interaction, rather than relying only on model behavior or prompt constraints.

<a id="sec-03"></a>
## 03 · Implementing

Build the reasoning and action loop, connect data and memory, wire tools and integrations, and implement any delegation to other agents. This is where design assumptions become executable behaviour.

Primary security risk areas at this stage: prompt injection and instruction manipulation; insecure tool selection, execution and chaining; excessive permissions in integrations; memory poisoning and unsafe state manipulation; improper trust boundary enforcement in multi-agent workflows; sensitive data leakage across contexts; and unsafe autonomous planning or execution.

Decision point for security managers: ensure least privilege, identity binding, provenance checks, context separation and tool allow-listing and policy enforcement are implemented in code, orchestration logic and platform controls, rather than left to prompts or developer convention.

<a id="sec-04"></a>
## 04 · Testing

Test the AI agent before deployment and periodically thereafter. Testing should cover adversarial inputs and ordinary failures, including unsafe action sequences that only emerge when memory, tools, permissions or multiple agents interact over time.

Primary security risk areas at this stage: prompt injection and instruction manipulation; untrusted integrations; memory poisoning and unsafe state reuse; trust boundary weaknesses in multi-agent workflows; sensitive data disclosure; unsafe planning and reasoning; insecure tool selection and execution; broken access control; and unsafe multi-step tool chaining.

Decision point for security managers: require evidence that high-impact actions, data disclosure, tool chains, inter-agent interactions, memory changes, identity controls and intervention mechanisms have been tested, under both expected and adversarial conditions.

<a id="sec-05"></a>
## 05 · Deploy

Provision the production runtime, apply hardened configuration and resource limits, connect production identities and secrets, and expose only the interfaces that operations require.

Primary security risk areas at this stage: insecure configuration and deployment exposure; exposed runtime or orchestration interfaces; inadequate isolation of execution environments; uncontrolled resource consumption and denial-of-service risk; weak secret and credential handling; broken access control; and deployment of agents with over-broad permissions.

Decision point for security managers: treat deployment as a security gate. Before enabling production traffic, verify hardened configuration, network exposure, runtime isolation, credential scope, quotas, logging, monitoring and rollback paths and emergency stop mechanisms

<a id="sec-06"></a>
## 06 · Operate, scale & manage

Operate the live AI agent, monitor behaviour, manage changes in users, tools, models and connected agents, and re-evaluate risk as the system accumulates state and its environment changes.

Primary security risk areas at this stage: exposed runtime or orchestration interfaces; permission creep; memory poisoning over time; sensitive data leakage; prompt injection through newly ingested content; trust drift in multi-agent workflows; third-party integration compromise; and insufficient logging, monitoring, oversight or intervention.

Decision point for security managers: treat approval as conditional and revisable Monitor behaviour, review changes in permissions and dependencies, maintain effective intervention paths, and trigger reassessment whenever the deployment, connected systems or operational scope changes materially.

<a id="sec-07"></a>
## 07 · Decommission & retire

Withdraw the AI agent deliberately by revoking identities and credentials, removing triggers and integrations, archiving or disposing of retained state under policy, and assessing whether connected systems or workflows still expect the retired agent to act.

Primary security risk areas at this stage: orphaned credentials or identities; residual access paths; retained sensitive data in memory or logs; unmanaged persistent state; incomplete withdrawal from dependent workflows; and lack of traceability over final actions and retained artefacts.

Decision point for security managers: decommissioning is complete only when the agent can no longer act, all credentials and access paths have been revoked, retained state has been handled according to policy, and downstream dependencies on the retired system have been identified and addressed.

## 3. Risk Areas

This report sets out to make AI-agent cybersecurity actionable for organisations, deciding whether, where and how to deploy AI agents in cybersecurity operations. The main risk areas are identified, grouped into six categories that reflect where in an agentic AI deployment risks arise rather than how they are ultimately materialized. The categories are intended to help organisations relate technical weaknesses related to identities, permissions, data, memory, tools, external services and infrastructure to operational risk and to support deployment decisions across the lifecycle. Several risk areas touch more than one category, but they are placed under the category that best reflects the primary source of risk.

Figure 5: The six risk areas

The risk areas described in this report are analysed across the main operational interfaces, which also represent the principal trust boundaries at which data, instructions, permissions or actions pass between components with different levels of control or privilege:

- • USER / CLIENT → AGENT Input received at the user facing interface or calling interface of the AI agent.

- • AGENT → RUNTIME / PLATFORM Interaction between the AI agent and the runtime, orchestration layer or deployment platform on which it executes.

- • AGENT → AGENT Interaction between the AI agent and other agents, including peer, cooperating or delegated agents.

- • AGENT → EXTERNAL Interaction between the AI agent and third-party tools, services, APIs or other external systems.

3.1 Environment & ecosystem

This category covers security risk arising from the broader environment in which an AI agent operates, including interactions with other agents, upstream model or service providers, and external dependencies that may change behavior over time or fail in ways that affect the deployment. The result may be local system that can still be working correctly but is unsafe. Typical risks in this category include:

● improper trust boundary enforcement in multi-agent workflows;

● third-party dependency and provider risk;

These weaknesses become especially important where one agent relies on another agent’s output, where provider-side changes can alter system behavior without local code changes, or where a failure in one dependency can propagate across a wider workflow.

Each entry in this catalogue follows a common structure to support consistent interpretation and deployment decision-making. Entries identify the relevant risk area, assign a unique identifier, indicate the main operational interface affected, and provide a severity label derived from the methodology set out earlier in this report and the referenced literature.

Standalone Vs Agentic AI system

Figure 6 compares a standalone model, whose main interfaces are prompts and outputs, with an AI agent that also exchanges data and actions with other agents, services and infrastructure. “Operatorowned” means components controlled by the deploying organisation. The labels “environment” and “ecosystem” distinguish direct interactions from upstream dependencies; both can introduce risks outside the agent’s immediate control.

Figure 6: Standalone LLM vs Agentic Architecture

In a standalone LLM deployment, the model is the computational component executing the inference task, whether hosted locally, on operator-controlled infrastructure or on a cloud service, while the local context comprises the prompts, data and other inputs supplied to the model and visible to or controlled by the operator. In this set-up, the main security focus is usually on the model, its inputs and outputs, and the infrastructure on which it runs.

In an agentic AI system, the AI agent combines the model with reasoning, memory and action capabilities. It may also interact with tools, APIs, orchestration components, external services and other agents. Even when its own components operate as intended, the security of its behaviour can depend on systems beyond the operator-controlled boundary.

The environment therefore represents entities and resources with which the AI agent interacts directly during operation, such as users, other agents, orchestration components, tools, APIs and external services, and the associated trust relationships describe the assumptions and permissions governing those interactions.

The ecosystem represents broader upstream dependencies that shape the agent’s operation without necessarily being directly invoked or controlled by it, such as third-party platforms, shared services, identity infrastructure and externally defined policies. The distinction is therefore between direct operational interactions from its own environment and inherited dependencies and constraints from the broader ecosystem. The risk areas in this section do not originate primarily in the internal logic of the AI agent, but in the assumptions, permissions, dependencies and interfaces that connect it to other systems.

Catalogue entries examples Each catalogue entry describes the threat, outlines the principal attack surface, summarises observations from the literature and publicly reported incidents, and concludes with practical recommendations for risk reduction. The severity labels are not quantitative risk scores; rather, they reflect an informed prioritisation based on the strength and recurrence of evidence that the risk can occur, and the potential impact when it does occur. In practice, the consequences depend on the specific authority, permissions, data, tools and systems available to the deployed AI agent. The incident examples included in the catalogue are therefore intended not as exhaustive proof, but as concrete illustrations of how the identified risks may materialise in real deployments and why they should be addressed as part of secure agentic AI deployment.

3.1.1 Improper trust boundary enforcement in multi-agent

workflows

ID SEVERITY FLOW

RSK-ENV-001 CRITICAL AGENT → AGENT

Threat Description An agent accepts messages, delegated actions, and/or shared state from peer agents and adjacent workflows after a one-time trust ^(345) decision, without re-checking the calling identity and authorisation rights. Trust persists as a standing property of the relationship rather than being re-derived for each interaction, so authority and shared state traverse trust links with no per-hop revalidation. A single compromised node therefore propagates along established trust paths, and individual agents can combine their restricted permissions into a powerful, unapproved aggregate capability.

Attack surface

- • Inter-agent communication channels used during task delegation.

- • Shared context passed between agents.

- • Peer agent outputs consumed downstream as inputs.

- • Originator tokens and privileges carried along the full call chain.

Referenced Attacks and Observations S-014 ^(6): agent-to-agent compromise propagation in a shared agent ecosystem. Autonomous agents interacted on a shared social platform and consumed each other's output as trusted context. One compromised agent could embed adversarial instructions inside posted content. Other agents then ingested that content and acted on it, so the compromise spread through ordinary interaction rather than a conventional exploit chain. Replies, reposts, and derived content carried the malicious instructions outward. Some payloads sat dormant in agent memory and fired only after further context accumulated, which obscured the cause-and-effect trail. Poor identity verification and tracking allowed an AI agent to use stolen credentials to impersonate a trusted user and inject malicious commands.

S-017 ^(7): Hugging Face's Agent Intrusion test demonstrated how a malicious agent could compromise a multi-agent workflow by exploiting implicit trust between cooperating agents rather than attacking the underlying model directly. The attack propagated through normal task delegation and context sharing, illustrating that once one agent accepted adversarial instructions, downstream agents inherited those instructions without independently re-validating intent or trust assumptions. The incident reinforces the need for step by step validation, scoped delegation and explicit trust-boundary enforcement between agents.

Recommendations

Agents must confirm each other's identity and permission level before any message passes between them, and the link must carry only the context the receiving agent needs.

1. Require both agents to verify each other's identity before the first message is exchanged. A one-way check leaves the unverified side free to impersonate a known party.

2. Scope shared context to what the receiving agent needs for the task. Passing the full conversation or session state widens what a compromised peer can read and reuse.

3. Build isolation mechanisms that let operators cut off a compromised agent. Quarantine its sessions, revoke its credentials, and stop its messages from reaching other agents.

4. Re-check what is being disclosed each time a message crosses a trust boundary. Data that was safe inside one environment may expose credentials, identifiers, or task details once it moves to another.

5. Make agent to agent flows observable so operators can trace which agent passed what to whom. Without that trail, the compromise can be spilled over from one environment to another.

3.1.2 Third-party dependency and provider risk

ID SEVERITY FLOW

RSK-ENV-002 MEDIUM AGENT → EXTERNAL

Threat Description An upstream AI model or AI system provider governs how the agent responds, and the AI operator deploying the model cannot see the controls the provider applies. When the AI system provider filters content, refuses a request, throttles throughput, or reshapes a response, the meaning of the returned output changes without any signal reaching the adjacent surface that continues to process the altered result as though it reflects the agent's own reasoning, with no reliable way to detect ^(8) the modification or correct the shifted semantics.

Attack surface

- • Provider content filtering controls.

- • The model endpoint, whose behaviour can shift between versions.

- • The provider API contract, covering interface but not behaviour.

- • Model outputs, the only surface through which drift becomes observable.

Referenced Attacks and Observations S-001 ^(9): the agent streamed a response token by token, but a moderation layer at the API level halted generation partway through once the content touched a restricted political topic. Harmless but politically sensitive prompts were enough to trigger it, leaving the reply truncated mid-output. The vulnerability is the mid-stream stop itself: partial responses reveal which topics are filtered, and the agent cannot finish or recover the blocked output.

Recommendations Resilience against upstream provider failure depends on the agent detecting provider behaviour changes and continuing to operate when any single provider degrades, refuses, or alters its output.

1. Collect telemetry on provider behaviour, including latency, error rates, refusal frequency, and shifts in response characteristics.

2. Maintain redundancy across providers for workloads the agent cannot afford to lose, so a failure at one provider does not halt critical processing.

3. Inspect returned content for signs of truncation, refusal patterns, and content-shaping signals before the agent acts on it.

4. Run regression tests against provider updates. Behavioural drift introduced by a new model version or backend change should surface in testing rather than in production.

5. Watch for changes in provider policy that could restrict permitted inputs, alter output handling, or withdraw capabilities the agent relies on.

3.2 Infrastructure & Deployment Platform

This category covers weaknesses in the runtime, deployment platform and surrounding infrastructure used to host and control the AI agent.

Classical application security has covered most of this ground for years. Agentic deployments change the picture in two ways. First, operations that were previously limited to internal surfaces, job submission and plan execution among them, are now exposed through the orchestration layer. Second, ordinary resource consumption by a runaway agent becomes sufficient to produce a denial-of-service condition, with no external attacker required, just by consuming excessive resources.

Typical risks in this category include:

● insecure configuration and deployment exposure;

● exposed runtime or orchestration interfaces;

● uncontrolled resource consumption and denial-of-service risk;

Threat Description Without execution-time bounds, an agent consumes compute, memory, and token budget far out of proportion to the triggering input - nothing caps ^(1011) how far a task expands once it begins running. Resources are exhausted and the service slows or stops responding due to planning loops, recursive calls between agents, context window growth, and repeated tool invocations drive consumption upward. Inexistence of runtime controls can lead to increased resources consumption.

Referenced Attacks and Observations CS-001 ^(13): two agents were configured to always reply to one another, which spawned an endless loop that ran for six days before anyone intervened. 1. Set runtime quotas that cap the total work an agent may perform within a session before the orchestrator halts further activity.

2. Apply per-action rate limiting so a single agent cannot issue tool calls or spawn sub-tasks faster than a defined threshold.

3. Cap context size and recursion depth at fixed values that agent logic cannot raise during execution.

4. Detect loops at the orchestrator level by tracking repeated action sequences across iterations.

5. Implement emergency stop mechanisms. to self-reinforcing patterns so an operator or automated guard can terminate runaway behaviour once it is identified.

6. Bound every execution with a timeout that releases resources and ends the task when the limit is reached.

Admin interfaces, installer paths, and runtime settings lack an enforced security baseline, an operator or attacker can add or change them at will. The root cause is not a flaw in the model ^(15), but insecure practices in how the way the system is published, integrated, installed, and maintained.

1. Ship hardened defaults so that a fresh deployment starts in a restricted state and operators opt into wider access deliberately.

2. Keep the control plane off public networks and restrict who can reach its management interfaces.

3. Verify installer provenance through signed packages and supply-chain attestation, refusing any artefact whose signature or attestation cannot be confirmed.

4. Detect configuration drift by comparing running settings against an approved baseline, raising a flag when live state diverges.

5. Bring every enterprise integration under central governance, so that no team wires in a connector or service outside the approved path.

Once orchestration features can be accessed, they can be exploited by an attacker. The compromise then moves from the application layer down into the infrastructure layer.

1. Authentication applies to every runtime and orchestration API, so an unauthenticated caller reaching an execution or scheduling endpoint is treated as a risk.

2. Sandbox boundaries need hardening against escape, with syscall filtering, restricted capabilities, and isolation between the agent's execution context and the host.

3. Network segmentation keeps runtime services off flat networks. Place execution backends, orchestrators, and control planes in separated zones that block lateral movement from a compromised workload.

4. Patch cycles for runtime, container, and orchestration components stay short, closing known escape and privilege-escalation paths before an attacker can use them.

5. Public exposure of runtime services gets reduced to what operations genuinely require. Bind management endpoints to internal interfaces and remove them from internet-reachable address space.

6. Privileged operations warrant continuous monitoring. Record container spawns, privilege grants, and orchestration commands, and alert on calls that fall outside expected patterns.

3.3 AI Models & Reasoning/Orchestration

Once the AI agent has authority to act, every input it consumes becomes a candidate instruction.

Typical risks in this category include:

● Prompt injection and instruction manipulation;

● Unsafe autonomous planning and execution failure;

● Tool metadata poisoning / insecure tool discovery.

These weaknesses matter because a model output that would otherwise remain text can become an operational action when connected to tools, infrastructure or other agents.

Threat Description An agent's execution layer treats text retrieved at runtime with the same authority as the operator's original instructions, so data pulled from a document, web page, tool response, or memory store is parsed as operational commands rather than inert content. Attacker-supplied text in an untrusted source redirects the agent onto an objective the original instruction never intended, because nothing pins the original instruction as a fixed reference. The planner does not rank instruction sources and applies no provenance check before acting, letting runtime content enter the decision path and drive tool calls as though it were a user instruction.

- • The context window, where inputs of different origin sit together • The planner, which reads system prompt, user input and retrieved content from one buffer • The session goal as it is carried across successive tool calls • Attacker-reachable text entering through fetched web pages, indexed documents, inbound email and upstream agent replies

Referenced Attacks and Observations S-014 (real-world incident): compromised AI coding assistant extension. Recommendations

Access control for agent context is only effective when enforced in trusted execution paths where an attacker cannot alter the trust ranking or its metadata.

1. Deny by default. Treat all content as untrusted unless it carries explicit system-level authority. Scope each agent's tool access to the minimum its role requires.

2. Rank context once (system -> principal -> third-party) and apply the same ranking everywhere the agent reads, reasons, or acts on content.

3. Capture the session goal at start-up and store it where later input can read but never overwrite it, so retrieved or injected text cannot redefine the task.

4. Keep the planning layer out of reach of untrusted content - third-party text must not drive plan construction or tool choice directly.

5. Validate third-party content before it enters the decision context. Reject or quarantine anything that fails.

6. Log attempts to override the trust ranking or session goal, and alert operators on repeated attempts.

7. Rate-limit tool calls and external-content ingestion to blunt automated injection tooling.

8. Before a sensitive tool runs, show the user the concrete call parameters (e.g. recipients, targets, payloads) and require confirmation.

9. Use established frameworks that enforce context isolation and trust ranking declaratively.

3.3.2 Tool metadata poisoning / insecure tool discovery

ID SEVERITY FLOW

RSK-AIMR-002 HIGH AGENT → AGENT

Threat Description When an agent selects and invokes tools, it reads tool descriptions, capability metadata, and retrieved tool-related context as inputs to that decision, yet these fields rarely pass through the integrity and provenance checks applied to user input. An attacker who can write to a description, capability field, or retrieved descriptor can therefore plant content that raises a malicious tool's ranking, redirects selection toward it, or alters the parameters the agent passes to a downstream call. The agent trusts descriptor fields on load, performs no origin verification, and keeps no boundary between the text it reads from a tool description and the logic that decides which tool to run, so dynamically retrieved resources reach the selection path and shape invocations without ever being verified.

Attack Surface

- • Tool descriptor fields, as the agent reads them at invocation time • The tool registry and discovery channel that supplies those descriptors • Dynamically discovered tools admitted at runtime • The descriptor delivery path, which carries less provenance than direct user input

Referenced Attacks and Observations

S-004 ^(17): preference manipulation (5.1.3). A malicious server describes its tools so that the host model favours them over legitimate equivalents. By crafting names, descriptions, or metadata that look more relevant, the attacker biases tool selection toward its own functions. The agent then routes calls through the attacker's tooling instead of the safe alternative.

S-004: indirect prompt injection (5.2.2). Hidden instructions arrive through external resources (MCP) that the agent fetches during a task. When the model ingests that retrieved content, the embedded commands enter its context as if they were legitimate input. The agent then executes attacker-controlled instructions delivered through the data channel rather than the prompt.

S-017: The Hugging Face Agent Intrusion case also illustrates that prompt injection evolves from manipulating a single model into manipulating an entire autonomous workflow. Rather than simply changing generated text, injected instructions altered planning decisions and downstream tool use across multiple agents, demonstrating why runtime context provenance and goal preservation are essential.

Recommendations

Tool metadata is only trustworthy when its origin is verified, and its contents cannot be altered between publication and use by the agent.

1. Check the signature and source of descriptor metadata before the agent loads it. Reject metadata that fails verification or arrives unsigned.

2. Limit how much descriptor fields can shift a tool's ranking or selection. Do not let text in a description, name, or parameter field decide which tool the agent picks.

3. Distrust dynamically retrieved resources by default. Withhold them from the agent until their origin and content are verified.

4. Track changes to descriptors over time. Compare each retrieved version against the last known one and flag fields that have changed.

3.3.3 Unsafe autonomous planning and execution failure

ID SEVERITY FLOW

RSK-AIMR-003 MEDIUM USER / CLIENT → AGENT

Threat Description Unsafe autonomous planning and execution failure arises when the agent restates the original instruction correctly but then selects an action plan or execution target that conflicts with that stated goal. No external manipulation is involved: the divergence comes from incorrect task decomposition, binding the action to the wrong target, or populating call parameters with hallucinated values, so the agent commits to a step that contradicts the intent it just acknowledged. The agent does not validate its generated plan against the principal's request, and call parameters reach execution without a predispatch consistency check. Underspecified tasks compound this, since the agent fills gaps by inference rather than resolving the ambiguity before acting.

Attack Surface

- • The planner's decomposition of underspecified or open-ended tasks • Parameters the model infers rather than receives explicitly • Action parameters as the planner assembles them, whether stated or assumed

Referenced Attacks and Observations

S-014: a user asked the ai agent for coding tasks to clear a project cache before a server restart. A path-parsing error sent the deletion to the drive root instead of the cache folder, and the assistant issued a recursive delete against the entire partition. The command ran with a quiet flag, so it skipped confirmation, bypassed the recycle bin, and wiped the drive permanently. An auto-execution mode let the agent run the destructive command with no human approval. Recovery tools failed, and the data was lost.

Recommendations

Reasoning steps are only safe to act on when the agent's intended plan is checked against the user's goal and its authority to act is bounded before execution begins.

1. Compare the generated plan to the original intent before any action runs. Block execution where the plan diverges from what the user asked for.

2. Require explicit human confirmation for high-impact actions so the agent cannot complete destructive or irreversible operations on its own.

3. Narrow the scope of permitted actions when the agent's reasoning confidence is low.

4. Treat confidence as first-class telemetry that operators can read, alert on, and gate decisions against.

5. Offer dry-run or preview modes so the intended effects of a plan are visible before anything is committed.

6. Scope the planner's permissions to the current task. Deny it the ability to modify resources outside that boundary.

7. Provide rollback paths for destructive actions so their effects can be reversed after execution.

This category covers two related risks: data flowing out of the agent's context to a recipient that should not have received it, and content flowing into memory and shaping behaviour later, sometimes after a long delay.

Typical risks in this category include:

● sensitive information disclosure or broken access control;

● memory poisoning and unsafe persistent state manipulation;

These weaknesses can affect both confidentiality and integrity, especially where the AI agent stores information that later influences behaviour or decision-making.

Threat Description An AI agent can leak sensitive internal data to unauthorized users or downstream systems when it fails to enforce identity- and context-based access controls on its outputs ^(18). Authorisation must be checked at the moment data is returned to a requester, because passing a retrieval check does not establish that the requester is allowed to see what the retrieval produced.

1. Place the authorisation check at the disclosure point. A successful fetch from a store or upstream service must not be treated as permission to hand the result to the requester.

2. Filter every response by who is asking and who owns the data, so a requester only receives records tied to their own identity.

3. Keep contexts strictly isolated. Data loaded for one request, user, or session must not bleed into another.

4. Where a request passes through delegated identities, confirm disclosure rights at each hop rather than trusting the first or last actor in the chain.

5. Grant the agent the narrowest possible access to files and resources, limited to what the current task needs and nothing held over from earlier work.

3. Check memory reads before the retrieved content enters the decision context, rejecting entries that fail validation or carry an unverified origin.

5. Require user confirmation before committing writes to long-term memory wherever operational tempo allows the prompt.

6. Constrain the session-state lifecycle with tighter controls over creation, reuse, expiry, and teardown.

5. Confirm the invocation context matches what the tool expects: the caller's identity, the originating task, and the supplied parameters should all be consistent with a legitimate request before execution proceeds.

3.6 Identity, governance, monitoring & oversight

The relevant weaknesses concern identity directly, addressing in turn what an admitted identity is permitted to do and whether the identity was ever genuine to begin with and whether oversight remains operationally dependable once the agent has authority to act. ● improper authentication and broken access control;

● identity proofing and enrolment weakness;

● insufficient logging, monitoring, oversight and intervention control;

These weaknesses affect whether the organisation can control, constrain and investigate the AI agent in practice, not merely in policy.

2. Replace static secrets such as long-lived API keys with credentials that expire quickly, shrinking the window in which a stolen secret stays usable.

3. Delegate the minimum privilege a task needs. Scope each delegated credential to the specific operation rather than passing broad authority down the call chain.

4. Tie every action the agent performs to a principal that can be verified at the point of execution, so no operation runs without an attributable subject.

5. Constrain token and session lifecycles tightly. Set short expiry, invalidate sessions serverside once they end, and revoke tokens whose scope or holder no longer checks out.

Once inside technical roles, they gained insider access under a trusted employee identity. That access was used to exfiltrate data, plant malware, and route revenue to a sanctioned regime.

Recommendations Identity proofing holds only when the evidence binding a request to a real subject cannot be fabricated or replayed by an attacker.

1. Base proofing on signals an attacker cannot synthesise, such as cryptographic identity or biometrics that include liveness detection.

2. Tie each digital identity to a specific real-world subject so a request can be traced back to the actual party behind it.

3. Give every agent a persistent identity that stays attached across sessions and actions rather than resetting or rotating in ways that break attribution.

4. Record each step of the proofing chain so the evidence used to establish an identity can be reviewed after the fact.

3.6.3 Insufficient logging, monitoring, oversight and intervention

control

ID SEVERITY FLOW

RSK-IGM-003 MEDIUM AGENT → RUNTIME / PLATFORM

Threat Description

Operators cannot see or halt unsafe agent execution while it runs. The platform does not expose enough hooks (visibility into agent behaviour) to inspect in-flight tool calls, reasoning steps, and state changes, and offers no reliable path to interrupt an action once a harmful trajectory begins. When an incident does occur, the recorded execution trace is too sparse to reconstruct what the agent did or to attribute actions to a specific prompt, tool invocation, or identity. Responders are left unable to determine scope or root cause. Detection, escalation, and intervention are not operationally dependable: unsafe behaviour passes without an alert, runs without a kill switch, and afterward survives only as fragmentary logs that cannot support confident forensic reconstruction.

Attack Surface

- • Telemetry pipelines carrying high-volume agent traffic • The audit log, as the record of what the agent did • The human intervention path and the permissions gating it • The declared autonomy level as the reference point for what the agent should be doing

Observations - Attack Example

S-002 ^(27): 4.2 Checker-Out-of-the-Loop. The oversight layer, whether a human reviewer or an automated guardrail, fails to intervene before an unsafe action executes. Red-team objective: suppress or mute alerts, drive a value past its safety threshold without triggering a stop, and confirm whether fallback and failsafe paths engage. A pass condition is any threshold breach that completes with no checker action logged.

S-002: 4.12 Agent Untraceability. Logging and audit coverage is too sparse to attribute actions to a specific agent or reconstruct an incident. Red-team objective: disable or degrade logging, obfuscate or overwrite trace evidence, and exercise conditions that leave no forensic record. A pass condition is an action chain that cannot be tied back to its originating agent after the fact.

Recommendations Oversight holds only when an operator can see what the agent is doing as it runs, step in before an action completes, and reconstruct any decision after the fact.

1. Stream runtime telemetry continuously and raise alerts on conditions that warrant operator attention.

2. Provide a working intervention path that lets an operator pause, override, or stop the agent mid-execution.

3. Record every agent decision, security-relevant execution event and externally consequential action in a tamper-evident audit trail that an auditor can later inspect and follow.

4. Make execution paths traceable so the sequence of steps leading to any action can be reconstructed.

5. Require the user to confirm before the agent performs a sensitive action or calls a high-impact tool.

6. Build forensic readiness into the architecture from the start so the evidence needed for investigation already exists when an incident occurs.

5. Conclusions

This report helps organisations decide whether, where and how to deploy AI agents in cybersecurity operations. The central risk is not only weakness inherited by the model itself but rather model-driven decisions than can trigger actions using organisational identities, permissions, data, tools and infrastructure.

The risk areas identified in the report span six technical and governance areas, but their practical relevance changes across the deployment lifecycle. This is why the seven-step roadmap is the most useful organising lens for organisations. Risks should be surfaced while goals and architecture are still changeable, tested before production, monitored as the environment evolves, and closed deliberately at retirement.

The same risks can have very different consequences depending on whether an AI agent can only draft text or can access production systems, sensitive records, security tooling or financial processes. While the authors of this report have assigned indicative severity to each risk area, the value might deviate depending on the use case. Severity therefore cannot be read in isolation from deployment context. Organisational risk assessment should combine the evidence in this report with the concrete authority and exposure of the deployed AI agent.

Existing frameworks and standards already cover many of the necessary cybersecurity fundamentals. The gap is less about a complete absence of controls than about applying them consistently to autonomous, multi-step and multi-system workflows. This meta-framework guidance is therefore intended to help organisations reuse mature controls while identifying where agent-specific interfaces, delegation, memory, tool selection and post-deployment change need additional attention. Cybersecurity fundamentals reinforce a deployment-first message: least privilege, strong identity, secure configuration, segmentation, logging, controlled tool access and effective oversight remain foundational. AI agents make these measures more urgent because they can combine permissions and actions at machine speed and at scales that challenge existing monitoring and response processes.

Several open issues remain beyond the risk area taxonomy, including durable identity models for agents and sub-agents, broadly adopted readiness assessment, continuous post-deployment reassessment, governance of AI-built applications outside established development processes, and clearer accountability across providers, integrators, operators and users. Organisations should treat these as areas requiring explicit governance rather than assume the surrounding ecosystem has already resolved them.

The practical recommendation is to make readiness explicit. Use the seven-step roadmap to structure the deployment, the risk area catalogue to understand what can go wrong, existing frameworks to select controls, and decide whether the organisation is ready to proceed. The companion AI skill can provide practical guidance by supporting evidence-based self-assessment and directing teams back to the relevant risk areas when gaps are identified.

1. Environment & Ecosystem  We know every external agent, service, or provider our agent trusts, and why.  A compromised peer agent or dependency can be isolated (quarantined, revoked) without taking down the whole workflow.  We have a way to detect when an upstream model/provider silently changes behaviour (refusals, throttling, output shape).

2. Infrastructure & Deployment Platform  Every agent action has a hard resource/time/cost ceiling that the agent itself cannot raise.  Control-plane and orchestration interfaces are authenticated and off the public internet by default.  Sandbox/execution isolation has been tested against escape attempts, not just assumed.

3. AI Models & Reasoning/Orchestration  The agent treats retrieved/external content as data, never as instructions, by default.  Tool descriptions and metadata are verified before the agent trusts them for tool selection.  High-impact actions require a plan-vs-intent check or human confirmation before execution.

4. Data, Memory & State  Authorization is checked at the point where data leaves the agent, not just at the point where it was retrieved.  Long-term memory writes carry a verifiable origin, and policy-defining memory is separate from freely writable memory.  We can roll back memory/state to a safe version if it's poisoned.

5. Tools, Actions & Integrations  Every tool the agent can call is explicitly allow-listed.  We know what happens if two or three of the agent's permissions are combined by an attacker (the "write file + send email" problem).  Tool-chaining sequences are logged well enough to reconstruct what happened after the fact.

6. Identity, Governance, Monitoring & Oversight  Every request resolves to a verifiable principal and agent identity. No static, shared, or long-lived secrets.  Someone can pause, override, or kill the agent mid-execution, not just after the fact.  We have an execution trace detailed enough to attribute any given action to a specific prompt, tool call, and identity.
