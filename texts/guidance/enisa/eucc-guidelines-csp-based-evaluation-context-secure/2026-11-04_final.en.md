## 1. INTRODUCTION

<a id="sec-1-1"></a>
### 1.1 OBJECTIVE

This guidelines document supporting the EUCC scheme provides guidance for the evaluation of applications using a Cryptographic Service Provider (CSP) and describes a methodology for such evaluations.

The use of a CSP addresses the scaling problem of the classical smart card composite approach when applications are intended to run on a variety of chip platforms. Unlike a cryptographic library, a CSP provides a defined set of complete and encapsulated security services such as protocols, signature creation, authentication via a harmonised API. The harmonised API realises a kind of an abstraction layer so that different CSP implementations on different chip platforms present the same behaviour to the applications.

The CSP implementations need to be certified at EAL4 augmented with AVA_VAN.5 using the classical smartcard composite evaluation approach. The advantage of the use of a harmonised CSP is that the applications do not need to implement highly critical security services, e.g., processing of secret keys. This may both:

- - help risk owners to accept a lower assurance level for the application.

- - avoid going for composite evaluations for each chip platform configuration intended to host the application. Instead of that, one composition certification according to CC class ACO can be conducted with a representative CSP implementation.

Different CSP types with different sets of security services and different API are possible. Within one CSP type, the implemented security services, and the API need to be the same for the different implementations on different chip platforms.

## 2. OVERVIEW

2.1 Problem description The Secure Element (SE) landscape is evolving from smartcards to embedded Secure Elements (eSE) and Secure Subsystem in System on Chip (3S in SoC). Applications for eSE and 3S in SoC platforms are usually loaded on the platform after their delivery to the end user and are intended to run on a wide range of different platform configurations. Applying the smartcard composite evaluation approach to those applications necessitates multiple reevaluations for each application [COMP]. This approach, requiring each application to be evaluated on every available platform, creates a geometrically scaling problem that is not practically feasible in the market of fast evolving mobile device platforms.

2.2 Objective This document describes an evaluation approach for SE Applications using composition as an alternative to [COMP]. The approach aims to streamline the certification process by introducing the Cryptographic Service Provider (CSP) as a cryptographic abstraction layer. This layer defines a universal security guidance for application developers and provides certified, application-ready security services through a harmonised Application Programming Interface (CSP API) supporting typical application use cases.

The goal of such a CSP-layer is to omit the need for individually physical testing on each platform for applications that employ the CSP API for all their security-related needs.

Applications for Secure Elements and classical chip cards may benefit from such a CSP-layer, supporting portability across platforms without requiring recertification, as illustrated in Figure 2, “Certify once, deploy across platforms”.

Figure 2: Certify once, deploy across platforms

2.3 Concept of the methodology The Target of Evaluation (TOE) is an application that relies on security services provided by a CSP. These CSP services cover application-specific security functionalities that are logically separated, self-contained and decoupled from the application. Furthermore, they are configured exclusively for the respective application – for example, the services provide cryptographic operations using TOE-specific key material.

As a result, all security functions invoked by the application via the CSP API are certified at EAL 4 + AVA_VAN.5 by the CSP certification. The application inherits de facto the security assurance from the CSP certification for the security functions used via on the CSP API. The TOE may still make use of functionality provided by the underlying platform, such as file management. However, if the TOE directly invokes security-related functionality from a component other than the CSP, such functionality falls out of the scope of this assurance inheritance and should be addressed through other means (e.g., by excluding the affected functionality through the TOE guidance).

The CSP itself may use the security features of the underlying platform and expose them via the CSP API. Such features are considered in the CSP’s own evaluation. Therefore, the CSP is evaluated using composite evaluation according to [COMP] including the operating system and hardware. The application, on the other hand, is evaluated following the CSP-based evaluation methodology defined in this document. This methodology combines EAL-based assurance assessment with ACO for the composition of the application and CSP, resulting in a unified evaluation process.

Note: Composite certification, as specified in [COMP], and ACO for composition, as specified in Section 15 of [CC2022-3R1], represent distinct evaluation approaches under Common Criteria (CC).

The required evaluation levels (including all direct and indirect dependencies) are as follows:

The TOE is evaluated at EAL2 augmented with ADV_IMP.1. In addition, it is evaluated as a composition with the corresponding CSP type at ACO_CAP-B.

The CSP is certified at EAL4 augmented with AVA_VAN.5.

For both, augmentations and higher assurance levels or packages are permitted.

EAL2 augmented with ADV_IMP.1, with dependencies ADV_TDS.3, ADV_FSP.4 and ALC_TAT.1, defines the minimum assurance level required for the SAR evaluation of the application. CAP-B defines the minimum assurance package required for its composition evaluation with the CSP. If needed, additional augmentations (e.g., ALC_FLR.2 for vulnerability handling or ALC_DVS.1 for development security) may be included. Higher assurance levels (e.g., EAL3 or EAL4) or a higher assurance package for the composition (CAP-C) are also applicable, while the benefit of eliminating the need for individual physical testing remains unchanged.

This approach, illustrated in Figure 3, allows considering the results of physical TOE tests executed on one specific CSP-enabled platform as representative for all other platforms supporting the same CSP.

Figure 3: CSP-based evaluation

2.4 Scope The CSP-based evaluation methodology described in this document is not restricted to a specific application scenario and may be applied to various use cases, such as digital identity (eID), payment systems, ticketing, access control, healthcare, automotive solutions, and others.

However, this methodology applies only to applications running directly on a CSP-enabled SE platform (CSP platform), meaning the application runs on the same SE platform as the CSP Implementation. Figure 4 illustrates this limitation.

Typical examples of applications supported by this methodology include:

- • Java Card applets operated on GlobalPlatform-compatible SEs with CSP support.

- • Native applications operated on proprietary SEs with CSP support.

Note: The CSP approach for inheriting security assurance from a cryptographic abstraction layer can also be applied to other system architectures, such as client-server models. A future version of this document may extend support to applications running on separate platforms or to CSP Implementations hosted on non-SE platforms.

However, we initially limited the scope to SE Platforms to keep the methodology simple as a starting point. Once we gain more confidence in the approach, we could consider expanding the scope by updating Section 1.4 and adjusting the document title.

2.5 CSP types Distinct system architectures, such as Java Card-based, native or MULTOS-based SE platforms, may require different types of CSPs. In such cases, the certification result of the Application is valid only for platforms that support the same CSP type.

A CSP type is characterized by the combination of a CSP PP and a CSP API specification:

CSP PP + CSP API = CSP Type

Thereby, the CSP API defines the harmonised interface across supported platforms, while the CSP PP specifies the hardware and operating system scope for which the CSP can be certified.

In addition to the CSP PP and CSP API, an applicable CSP guidance document and CSP test specification are required for the evaluation and use of a CSP type under this methodology. The applicable versions of these documents are therefore identified as part of the evaluation.

In summary, the following documents are required for the evaluation and use of a CSP type under this methodology:

- • CSP PP: A Protection Profile that defines the security requirements for CSPs.

- • CSP API: A standardised interface specification that serves as a security abstraction layer, offering certified security functionalities for applications.

- • CSP guidance: A universal security guidance document that applies to all CSP products of a specific CSP type. It defines rules for applications to securely operate on all platforms implementing that CSP type.

- • CSP tests: A CSP compliance test specification to verify whether a CSP-enabled platform is conformant to the CSP API.

In case a CSP API defines optional features or operations, these documents define how to ensure that an application can be operated only on CSP platforms providing all the features required by the application. This may, for example, be achieved through compatibility checks enforced by CSP guidance rules. However, this and other requirements for CSP types are specified in Annex 1: Requirements for CSPs. Only CSP types fulfilling these requirements are applicable for this methodology.

Figure 5: Different SE architectures may require different CSP types

In addition, CSP types may offer different security functionalities, addressing different technologies and/or scenarios. However, all CSP types ensure that the security services they provide meet the following criteria:

- • Logically separated: The security services provided by the CSP operate independently from the internal logic of the application. This ensures that the CSP's security mechanisms remain unaffected by potential vulnerabilities or errors in the application, clearly separating the CSP's responsibility for security enforcement from the application's operational logic.

- • Self-contained: The CSP implements its security functionalities as standalone components, independent of the application's state or behaviour, provided that the application adheres to the CSP guidance. It maintains cryptographic keys, security-critical data and its own operational state to ensure integrity and confidentiality under all operational conditions.

- • Decoupled: Interaction between the application and the CSP is restricted to well-defined interfaces (i.e., the CSP API). This ensures that application changes or updates do not compromise the functionality or security of the CSP. Moreover, it simplifies the evaluation of the application by clearly separating the CSP’s security services from the application's logic.

To provide logically separated, self-contained and decoupled CSP services, the CSP is pre-configured with a defined set of cryptographic keys, certificates, corresponding algorithms, etc.— collectively referred to as the CSP configuration. Authorised applications can invoke these pre-configured security services (i.e., the CSP services) without introducing new security risks or requiring custom security functionalities.

For further details on CSP types and corresponding sample architectures, see the annexes, which provide additional information related to Cryptographic Service Providers (CSPs). Annex 1 specifies the requirements for CSPs. All further annexes are informative, as they illustrate typical CSP specifications, services, and configuration options and serve as examples of how CSPs can be used.

The following overview summarises the content of each appendix:

- • Annex 1: Requirements for CSPs

Lists requirements for CSP PP, CSP API, CSP guidance, CSP tests and CSP platforms that establish the conditions under which an application evaluation according to this methodology would be considered valid.

- • Annex 2: Sample CSP Services

Lists cryptographic and security-related functionality typically provided by the CSP, such as cipher and signature operations, secure messaging, and PIN management.

- • Annex 3: Sample CSP Configuration

Provides an example of how to configure a CSP to offer cryptographic operations that already include TOE-specific key material.

- • Annex 4: Sample CSP Multi Applications Support

Describes how multiple applications with different or conflicting use cases can be supported on the same Secure Element and how isolation is ensured; for example, two eID Applications from different countries using the same CSP platform.

- • Annex 5: Sample CSP User-Level Authorisation

Explains different concepts for identification, authentication and authorisation of both Applications and real-world users interacting with them.

- • Annex 6: Sample CSP Platform Dependencies

Details how CSP implementations can expose existing security functionality of the underlying platform without reimplementing cryptography, instead encapsulating it as a cryptographic abstraction layer in line with this methodology.

- • Annex 7: Sample CSP within eUICC

Note: The CSP guidance eliminates the need for platform-specific security instructions by defining CSP type-specific rules for security concerns that cannot be fully enforced by the CSP due to technical limitations or practical constraints. Applications need to adhere to these rules. For example, the guidance may specify CSP API methods where the use of sensitive arrays for input and output parameters is required to ensure data integrity.

2.6 Security assurance and composition This CSP-based evaluation methodology, as introduced in Section 2.3, combines SAR-based assurance assessment with ACO Composition evaluation into a unified evaluation process with the following characteristics:

- • Combined ST: SAR and ACO evaluation is performed using a single Security Target (ST).

- • Unified TOE definition: The TOE is the application using a CSP type, treated as a single entity for both SAR and ACO evaluation.

- • Flexible evaluation levels (EAL2 augmented to EAL4 augmented): Certification is available at EAL2, EAL3 or EAL4, each augmented with at least ADV_IMP.1 including dependencies.

- • Relying on CSP functionality: Security aspects covered by the CSP’s certification do not require separate Security Functional Requirements (SFRs) or revalidation.

- • Custom security functionality: Application SFRs are kept at a minimum. If such SFRs, or any of their dependencies, require platform security mechanisms, they rely exclusively on CSP API operations.

- • Composition evaluation: The application's integration with the CSP is evaluated against ACO (ACO_COR.1, ACO_CTT.2, ACO_DEV.2, ACO_REL.1, ACO_VUL.2), using one representative CSP platform as the base component, in alignment with the SAR evaluation.

- • Unified testing and documentation: A single evaluation testing process covers both TOE SFRs and CSP integration, using one representative CSP platform for physical testing.

Note: The representative CSP platform is selected by the application developer with no specific selection criteria, as the CSP provides a uniform abstraction layer with the same API and security services, ensuring identical functional behaviour across different CSP implementations.

Chapter 5 defines SAR, specifying the Application’s security evaluation tasks under this methodology. Key aspects include:

- • ASE (Security Target Evaluation): The Security Target (ST) specifies the CSP type and versions the application is compatible with, and list the high-level CSP services used.

- • ADV (Development): The application’s implementation representation demonstrates correct use of the CSP API and adherence to the CSP guidance. The TOE design explains the CSP configuration and the security-critical data flows between application and the CSP.

- • ALC (Life-cycle): The CSP configuration, as part of the TOE, is uniquely identified and subject to controlled modification.

- • AGD (Guidance): Deployment and initialisation of the TOE is fully specified, including the personalisation of the application and its corresponding CSP configuration.

- • ATE (Tests): Functional tests are performed on at least one representative CSP platform. The results are applicable to any other CSP platform with the same configuration.

- • AVA (Vulnerability Assessment): Physical vulnerability tests are conducted on one representative CSP platform, following the same approach as functional tests.

Chapter 6 defines ACO specific requirements, specifying composition evaluation of the application with a CSP platform as base component. Key aspects include:

- • ACO (Assurance Composition): The application integration is evaluated against harmonised specification documents of the CSP type, including CSP PP, CSP API, CSP guidance and CSP tests, and re-uses test results from ATE and VAN evaluation.

Note: The CSP tests are not re-evaluated during the application evaluation. However, the evaluator checks that they exist and that they cover the CSP functions required by the application (see 6.2).

2.7 Product or platform change Application certification remains valid on any CSP platform that conforms to the same CSP type, including the CSP PP, CSP API, CSP guidance and CSP tests versions considered during evaluation. This means that a certified application can be transferred to another CSP platform of the same CSP type and versions without requiring re-evaluation. However, this applies only to CSP types that fulfil the requirements defined in Annex 1: Requirements for CSPs.

In case of changes to the Application, the standard maintenance, re-evaluation and re-assessment processes according to Annex IV of [EUCC] apply.

For CSP Platform changes, re-certification of the application is not required as long as:

- • The new CSP platform remains compatible with the CSP type and the applicable versions of its CSP PP, CSP API, CSP guidance and CSP tests considered during evaluation.

- • The certification status of the CSP platform remains valid.

If a CSP platform undergoes changes that invalidate its conformance to the CSP type, the application may no longer be operable without re-evaluation.

2.8 Certificate And Certification Report The Certificate and Certification Report follow the standard EUCC structure and content, providing the formal outcome of the SAR evaluation of the application, combined with the ACO evaluation of its composition with the CSP in a single Certificate and a unified Certification Report.

The Certificate complies with the requirements of [EUCC]and additionally includes:

- • Product Name: <<Application Name>> using <<CSP Type Name>>

- • Composition Statement: Relies on CSP security functionality as defined by <<CSP PP>>

- • CSP API: <<CSP API Name + Version>>

- • Evaluation Assurance Level: <<TOE EAL>> with composition based on <<CSP PP EAL>>

- • Composition Assurance: <<Composition Assurance Package + Components>>

- • TOE Evaluation Platform: <<CSP Platform Name + Version>>

The Certification Report also follows [EUCC] and further extends it by documenting:

- • Tested CSP platform: Specification of the exact CSP platform used for testing activities during the evaluation, including details such as platform name, platform version, operating system version, CSP Implementation version and tested configurations.

- • Information that the application can be transferred to compatible CSP platforms.

For a complete list of Certificate and Certification Report contents, see Chapter 8.

2.9 Benefits of this methodology This methodology defines a scalable certification approach by certifying applications against a CSP Type rather than a specific CSP implementation. As a result, an application evaluated once under this methodology keeps its certification status when used with any CSP Implementation that conforms to the CSP PP, CSP API, CSP guidance and CSP test specifications.

Compared to traditional composite evaluations according to [COMP], this approach introduces the following structural differences:

- • Certify Once, Deploy Across Platforms → Applications do not require re-evaluation for each CSP Implementation if the CSP conforms to the defined CSP type.

- • Decoupling of Application and CSP Certification → Applications and CSP implementations are evaluated separately, reducing dependencies in the certification process.

- • Optimised Certification Effort → Avoids redundant Common Criteria evaluations for every platform, improving efficiency.

- • Adaptability for CSP Implementations → CSP vendors can develop new implementations that conform to the CSP type without requiring re-evaluation of certified applications.

This methodology establishes a modular evaluation model, enabling certification of applications relying on CSPs while maintaining compatibility across multiple CSP implementations.

## 3. EVALUATION ACTIVITIES

This chapter defines the evaluation activities required for the evaluation of an application using a CSP. The evaluation has to ensure, among others, that the application:

- • Does not process highly critical assets (e.g., secret keys) on its own.

- • Implements the standard security measures as described in the generic CSP guidance.

- • Matches the CSP type of the base component.

3.1 STEP 1: PREPARATION PHASE In this step, the evaluator ensures that the necessary input for the evaluation is available.

The evaluator checks that all EVALUATION INPUT MATERIAL defined in Chapter 4 is available for evaluation.

The evaluator checks that the application ST specifies the versions of all referenced EVALUATION INPUT MATERIAL.

3.2 STEP 2: TEST SETUP In this step, the evaluator ensures that the test setup is suitable for evaluation activities.

The evaluator checks that the TOE can be deployed and operated using the testing deliverables listed in Section 4.3, ensuring that the test environment is correctly set up.

If deployment issues arise, evaluation activities not requiring direct TOE execution may proceed.

However, ATE and AVA testing will be postponed until the deployment issues are resolved.

3.3 STEP 3: SECURITY ASSURANCE EVALUATION (SAR) In this step, the evaluator ensures that the evaluation includes the minimum required assurance components and refinements.

The evaluator performs the SAR evaluation considering the SAR REFINEMENTS specified in Chapter 5 and the EAL specified in the ST of the Application.

Supported evaluation levels are EAL2+, EAL3+ and EAL4+, requiring at minimum the augmentations ADV_IMP.1, ADV_TDS.3, ADV_FSP.4 and ALC_TAT.1.

If the EAL in the ST does not meet these requirements, the evaluation cannot proceed.

3.4 STEP 4: COMPOSITION EVALUATION (ACO) In this step, the evaluator ensures that the evaluation includes the minimum set of ACO components including refinements.

The evaluator performs the ACO evaluation considering the ACO Refinements specified in Chapter 6 and the CAP level specified in the ST of the Application.

Supported composition assurance packages are CAP-B and CAP-C. At minimum, CAP-B is required by this methodology.

If the ST specifies a CAP level lower than CAP-B, the evaluation cannot proceed.

Where the same assurance components are required by both the chosen EAL (including augmentations) and the selected CAP package, the same documentation and results are used. No duplication is required, and higher component levels from the EAL also satisfy the corresponding CAP requirement.

3.5 STEP 5: FINAL ASSESSMENT AND CERTIFICATION The certification body reviews test results and creates the Certificate And Certification Report according to Section 2.8.

Key aspects of Section 5.1, ASE – Security Target evaluation:

Key aspects of Section 5.3, ALC – Life-cycle support:

- • ALC_CMS: The CSP configuration is included within the configuration management scope.

- • ALC_CMC: The CSP configuration, as part of the TOE, is uniquely identified and subject to controlled modification.

Key aspects of Section 5.4, AGD – Guidance Documents:

- • ATE_IND: Independent testing is performed at least on one representative CSP platform.

Key aspects of Section 5.6, AVA – Vulnerability Assessment:

- • AVA_VAN: Vulnerability testing is performed at least on one representative CSP platform.

Editor’s note: Despite this document is a guidelines document and does not enforce any additional requirement to EUCC, the following ACO refinements are using the CC terminology and therefore “shall” statements.

5.1 ASE – SECURITY TARGET EVALUATION These refinements ensure the Security Target (ST) correctly specifies CSP dependencies and usage.

5.1.1 ASE_SPD – Security problem definition The Security problem definition (SPD) complies with ASE_SPD as defined in [CC2022-3R1], with the following refinement for CSP-based evaluation:

ASE_SPD.1.4C:

The security problem definition shall describe the assumptions about the operational environment of the TOE, including an explicit assumption (A.Plat-CSP) that the CSP platform used by the TOE is assumed to conform to the required CSP type, including compliance with the specified versions of the CSP PP, CSP API, CSP guidance, and CSP tests, with their versions explicitly specified in the ST.

Rationale:

This refinement is required because correct operation of the TOE under this methodology requires a CSP platform that is consistent with the CSP PP, CSP API, CSP guidance, and CSP tests. Adherence of the TOE to the CSP API and CSP guidance, as verified in refinements to ADV, is important but not sufficient.

5.1.2 ASE_TSS – TOE summary specification The TOE Summary Specification (TSS) complies with ASE_TSS as defined in [CC2022-3R1], with the following refinement for CSP-based evaluation:

ASE_TSS.1.1C:

The TOE summary specification shall describe how the TOE meets each SFR and, for each SFR, shall list the high-level CSP services used to fulfil it, including the assets used by these services.

Rationale:

This information is necessary for the evaluator to obtain an overview that is required to verify that the application correctly uses the high-level CSP services, as needed for the evaluation of the refinements to ADV.

5.2 ADV – DEVELOPMENT These refinements ensure that the application correctly integrates with the CSP type.

5.2.1 ADV_IMP – Implementation representation The Implementation representation (IMP) complies with ADV_IMP as defined in [CC2022-3R1], with the following refinements for CSP-based evaluation:

ADV_IMP.1.1C:

The implementation representation shall define the TSF to a level of detail such that the TSF may be generated without further design decisions, and shall additionally

  - • include exact information on when and how the application invokes API operations relevant for fulfilling SFRs (covering security-relevant API operations provided by the CSP, the operating system, third-party libraries, and hardware),

  - • for all SFRs that rely on CSP services, show that the application does not directly invoke security mechanisms provided by the operating system, third-party libraries, or hardware,

  - • show that the SFR-enforcing functionality of the application does not re-implement security functions already provided by the CSP, and • show that the application adheres to the CSP guidance.

ADV_IMP.1.3C:

The mapping between the TOE design description and the sample of the implementation representation shall demonstrate their correspondence, and for all SFRs that rely on CSP services, show that the CSP API operations invoked by the application are consistent with the high-level CSP services and associated assets described in the TOE summary specification.

Rationale:

These refinements are required to ensure that the evaluator verifies the correct and secure use of CSP services by the application. In particular, they clarify that the application consistently invokes CSP API operations as described in the TSS, avoids bypassing or duplicating CSP security functionality, and adheres to the CSP guidance.

5.2.2 ADV_TDS – TOE design The TOE design (TDS) complies with ADV_TDS as defined in [CC2022-3R1], with the following refinements for CSP-based evaluation:

ADV_TDS.3.4C:

The design shall provide a description of each subsystem of the TSF, including a detailed description of the CSP configuration defining the CSP-managed assets (e.g., cryptographic keys, certificates, passwords) and their security-relevant parameters (e.g., algorithms, key sizes, security policies).

ADV_TDS.3.5C:

The design shall provide a description of the interactions among all subsystems of the TSF, including the flow of security-critical data between the application and the CSP.

ADV_TDS.3.7C:

The design shall describe each SFR-enforcing module in terms of its purpose and relationship with other modules and shall demonstrate that the application does not manage critical security assets, which are expected to be managed exclusively through the CSP configuration.

Rationale:

These refinements are required to ensure that the TOE design provides a structured and complete description of how the application uses the CSP, its interaction with the CSP, and the use-case-specific CSP configuration used to define and manage security-relevant assets.

5.3 ALC – LIFE-CYCLE SUPPORT These refinements ensure proper configuration management of the application-specific CSP configuration throughout the TOE life cycle.

5.3.1 ALC_CMS – Configuration Management Scope The Configuration Management Scope (CMS) complies with ALC_CMS as defined in [CC2022-3R1], with the following refinement for CSP-based evaluation:

ALC_CMS.2.1C:

The configuration list shall include the TOE itself; the evaluation evidence required by the SARs; and the parts that comprise the TOE, including the CSP configuration that is delivered with the TOE for the application use case.

Rationale:

This refinement ensures that the CSP configuration delivered with the TOE is included within the configuration management scope.

5.3.2 ALC_CMC – Configuration Management Capabilities The Configuration Management Capabilities (CMC) complies with ALC_CMC as defined in [CC2022-3R1], with the following refinement for CSP-based evaluation:

ALC_CMC.2.2C:

The CM documentation shall describe the method used to control changes to the CSP configuration, including version control and the secure deactivation or deletion of configuration items.

Rationale:

This refinement is required to ensure that the CSP configuration is version controlled and subject to controlled modification throughout the TOE life cycle.

5.4 AGD – GUIDANCE DOCUMENTS These refinements ensure correct deployment of the TOE.

5.4.1 AGD_PRE – Preparative procedures AGD_PRE.1.1C:

The preparative procedures shall describe all the steps necessary for secure acceptance of the delivered TOE in accordance with the developer's delivery procedures, including the security-relevant assets required for TOE deployment and their role in the secure initialisation of the TOE.

AGD_PRE.1.2C:

These refinements are required to ensure that the TOE, including the CSP configuration, is correctly and securely deployed to the CSP platform.

5.5 ATE – TESTS These refinements ensure all testing is performed on a single CSP platform that serves as a representative implementation of the CSP type.

5.5.1 ATE_FUN – Functional Tests The Functional Tests (FUN) complies with ATE_FUN as defined in [CC2022-3R1], with the following refinement for CSP-based evaluation:

ATE_FUN.2.1D:

The developer shall test the TSF and document the results on at least one representative CSP platform.

Rationale:

This refinement allows developer functional testing on one representative CSP platform, since (ASE_SPD.1.4C) all CSP platforms conform to the same CSP API and PP, (ADV_IMP.1.1E) the application follows the CSP guidance and implements no cryptography, and (ADV_TDS.3.2E) no highly critical assets exist at the application layer.

ATE_IND.1.2E:

Rationale:

5.6.1 AVA_VAN – Vulnerability Analysis The Vulnerability Analysis (VAN) complies with AVA_VAN as defined in [CC2022-3R1].

The evaluator determines that the TOE design identifies the security-critical data exchanged between the application and the CSP and relates these data flows to the corresponding CSP-managed assets and their security properties.

The evaluator further determines whether the handling of security-critical data within the described data flows is appropriate with respect to the required security properties of these assets, such as confidentiality, integrity, authenticity, or availability. In particular, the evaluator examines whether the data flows are constrained to CSP services that provide the required protection properties for the respective assets.

The evaluator is reminded that the objective of this examination is to assess the consistency of the TOE design with the defined security requirements of the assets. The evaluator does not assess the correctness of the technical implementation or the effectiveness of the underlying protection mechanisms.

7.1.4.3 Work Unit ADV_TDS.3-21 (Management of critical assets) The evaluator shall examine the TOE design to determine whether critical security assets are not managed by the application and are instead managed through the CSP.

## B ANNEX 2: SAMPLE CSP SERVICES

CSP services encapsulate security functionalities so that applications can rely on them and inherit the CSP’s security assurance (see Sections 2.5). Amendment N – CSP [GP-AMD-N] of the GlobalPlatform Card Specification describes how to implement such services using Java Card and GlobalPlatform technologies. Examples include:

- • Cipher and signatures: Ready-to-use cryptographic operations for encryption, decryption, signing and verification that utilise pre-configured cryptographic keys and fixed algorithms. Authenticated Applications can securely invoke them in a controlled manner, allowing them to inherit CSP security assurance.

- • Encryption transformations: An atomic cryptographic operation that converts already-encrypted data from one key and algorithm to another, using pre-configured keys and fixed algorithms. This enables authenticated applications to securely handle sensitive data without ever accessing it in plaintext, ensuring protection even if the application is compromised.

- • Secure messaging: A CSP-managed secure channel protocol flow that ensures the correct sequence of steps for each authentication protocol while using pre-configured cryptographic keys and certificates. Typical protocols include EACv1 for MRTD, EACv2 for eID, PACE-only, PACE-CAM and SCP03.

- • Attestations: Provides mechanisms to retrieve signed evidence from the CSP that verifies the authenticity and identity of critical components, such as platform attestation to prove the identity of the SE platform, CSP self-attestation, proof-of-possessions of key pairs, and attestations for counter values or other elements managed by the CSP.

- • Counter and limits: Support for secure counters that can be incremented either by the application or automatically by the CSP. Examples include usage counters that track the number of times a specific key is used in CSP services. Fixed limits on these counters enforce security policies, such as preventing the use of keys whose usage limits have been exceeded.

- • Timer and time management: Supports a system time that the CSP can use to evaluate timers, such as validity periods for keys, certificates or passwords. It also enables use-case-specific timers with fixed expiration dates, for example, to verify whether a person is over 18.

- • PIN and passwords: Manages PINs and passwords, including authentication status, retry counters, blocking and PUK-based unblocking, all handled within the CSP’s secure environment.

- • Secure auditing: Logs asset usage events (e.g., signature creations), security incidents (e.g., password failures) and system events (e.g., time updates). The CSP ensures the integrity of these logs by incorporating a counter and/or timestamp and signing it.

Such CSP services are provided through the CSP API, ensuring that applications can securely use them without directly handling assets or impacting security properties. This enables the reuse of CSP’s security functionalities without requiring their separate evaluation under this methodology.

The CSP API defined in GlobalPlatform Amendment N [GP-AMD-N] is complemented by the CSP Guidance for Applet Developers [GP-GUI-CSP], which provides security rules for Java Card applets using the GlobalPlatform CSP. Such rules are, for example, intended to ensure the secure interaction between the Client Application and the CSP. For instance, security-sensitive results returned by CSP operations shall be verified using the CSP's sensitive result verification mechanism. Non-compliance with this guidance may invalidate assumptions on which the application evaluation relies and may therefore affect the applicability of the CSP security guarantees to the application.

Together, the GlobalPlatform documents [GP-PP-CSP], [GP-AMD-N] and [GP-GUI-CSP] constitute a concrete CSP Type, the “GlobalPlatform CSP for Java Card Applets”. Other CSP Types, such as a “CSP for HSM solutions” or a “CSP for non-Java Card-based SE Applications”, may use the same CSP API as defined in [GP-AMD-N] but different Protection Profiles to support different hardware platforms.

## C ANNEX 3: SAMPLE CSP CONFIGURATION

Typical CSP services, such as those in Annex 2: Sample CSP Services, rely on pre-configured cryptographic assets, such as keys, certificates and passwords. These assets are securely managed within the CSP, preventing exposure or misuse.

Before Applications can use CSP services, the CSP is first initialised with these assets. This is referred to as the CSP configuration, which is typically done using a script.

Different CSP types manage their CSP configuration(s) in various ways. Simple CSP types may have a fixed, hardcoded configuration embedded in the CSP, with no possibility for modification. Most CSP types offer an administration interface, allowing administrators to adjust the CSP configuration based on the application needs, following the lifecycle phases shown in Figure 6.

Figure 6: Sample lifecycle for typical CSP types

In the configuration phase, an administrator sets up the CSP configuration. Once configured, the operational phase begins, allowing the application to use cryptographic services with the predefined assets.

Examples of a CSP configuration include:

- • Creating slots for assets such as cryptographic keys, certificates or passwords.

- • Configuring asset properties, including key size, curve, password length and certificate type.

- • Restricting asset usage to a specific CSP service and algorithm.

- • Configuring authentication and access control per application and CSP configuration.

- • Importing certificates, initialising passwords, and setting cryptographic key values via import, random key generation or key derivation functions.

To ensure that assets from the CSP configuration remain securely managed within the CSP while still being usable by applications, CSPs support asset handles. Each asset is assigned a unique identifier, managed within the CSP and shared with the application.

Using this identifier, applications can invoke CSP API operations without directly handling sensitive assets, ensuring controlled access to CSP services while keeping all processing within the CSP’s tamper-proof environment, preventing unauthorised exposure or misuse.

More advanced CSP types may allow CSP configuration modifications even during the operational phase. However, CSP services offering such CSP management operations still adhere to the encapsulation principle, ensuring security and preventing direct asset manipulation by the application. This can be achieved, for example, through:

- • Fine-grained access control at the asset level, e.g., restricting key generation within the CSP to specific assets and asset states.

- • Support for key agreement (e.g., ECKA-DH) and key derivation (e.g., AES-CMAC KDF, HKDF) through CSP services, while ensuring that all key manipulations remain within the CSP.

- • Double encryption layers for importing certificates or keys, using both a secure channel and asset-level encryption.

- • Cryptographically secured rollover mechanisms for certificate management (e.g., TA Linked).

- • Secure password change procedures, ensuring that passwords are updated only in a single atomic operation after verifying the old password, using an encryption mechanism.

- • Secure offloading, allowing encrypted assets to be exported and later re-imported, ensuring that only the originating or clustered CSP instances can decrypt them.

Figure 7 illustrates a sample CSP configuration with two slots for cryptographic keys (one imported, one generated), two slots for passwords (one PIN, one PUK) and fine-grained access control configuration for each asset. Unique asset identifiers are set within the script.

Figure 7: Sample CSP configuration

Note that some assets exist outside the CSP configuration but are required for CSP initialisation, such as for deployment and administrative authentication. Protection and verification of these assets are the responsibility of the CSP Admin in the operational environment, not of the CSP TOE itself. Related aspects are addressed in the refinements to ADV_TDS (see Section 5.2.2).

Examples of such deployment-related assets include:

- • Keys for remote management of the SE platform.

- • Keys to access the Security Domain (SD) of the CSP instance and/or application.

- • Data Encryption Keys (DEK) used for loading sensitive data into the CSP instance.

- • Assets imported into the CSP instance during initialisation or operational use.

Conclusion: Assets managed by the CSP enable applications to rely on CSP services without requiring direct handling or additional security measures. While these assets are securely encapsulated within the CSP, deployment and authentication assets may require additional safeguards to ensure a secure initialisation process.

## D ANNEX 4: SAMPLE CSP MULTI APPLICATIONS SUPPORT

A key architectural decision for CSP types is whether they should support multiple applications use cases running in parallel on the same CSP platform.

To ensure strict separation between different application use cases — such as eID applications from various countries running on the same SE — the CSP supports the concept of CSP instances, as illustrated in Figure 8.

Each CSP instance has its own dedicated CSP configuration, ensuring that only authorised applications can access the relevant CSP services for their specific use case. When an application is removed or revoked, its CSP instance can be securely deactivated or deleted, ensuring no residual sensitive data remains accessible.

A CSP instance can be implemented as a separate system process or as a virtual instance within a shared process (e.g., as separate threads). Regardless of the implementation approach, the CSP should ensure that assets, configuration data, services and authentication for each use case remain strictly isolated. This requirement is addressed in the CSP PP (see Annex 1: Requirements for CSPs).

Figure 8: Sample CSP multi applications support

For example, the GlobalPlatform-CSP, as specified in [GP-AMD-N], utilises the install "for install and make selectable" command from [GP-CardSpec] to create dedicated CSP instances for each application use case. This process involves different types of administrators, including:

- • SE administrator: Typically the SE owner with management privileges over the SE. This role is responsible for creating a new CSP instance dedicated to an application use case and granting access rights to manage its Security Domain (SD) to a CSP administrator.

- • CSP administrator: Typically the application developer responsible for a specific application use case. The CSP administrator creates the CSP configuration, authorises applications and transitions the CSP instance to OPERATIONAL state, allowing authorised applications to use its CSP services for the intended use case.

In this architecture, isolation between different Application use cases is enforced through platform mechanisms such as GlobalPlatform Security Domains (SDs), as defined in [GP-CardSpec]. This is achieved through dedicated key management, strict access control policies and cryptographic domain separation, ensuring that administrators and applications can only interact with their respective CSP instance.

<a id="sec-e-annex-5-sample-csp-user-level-authorisation"></a>
## E ANNEX 5: SAMPLE CSP USER-LEVEL AUTHORISATION

In addition to authentication and authorisation mechanisms for applications using CSP services, a CSP type may also need to support user-level authentication and authorisation. This is particularly relevant in scenarios where an application using a CSP is accessible by multiple users.

These scenarios can be addressed through the following CSP security features [GP-AMD-N]:

- • Access Control Rules (ACRs): Fine-grained access control per asset and application restricts CSP services to authorised Applications. The CSP needs to be able to unambiguously identify Applications to enforce these ACRs. Remote Applications running on a different platform than the CSP even require additional authentication mechanisms.

- • Secure Channels: User authentication via secure channels between Off-Card Entities (OCE) and the CSP, routed through the application. The CSP needs to enforce that its CSP services can only be invoked when a secure channel is established (e.g., PACE authentication). CSPs that support remote applications need to restrict CSP service invocation to occur exclusively through the secure channel.

- • Policies: Dynamic, asset-dependent policy rules, configured and enforced within the CSP, can restrict CSP services based on conditions. For example, access to a CSP’s signing service may require successful verification of a user PIN (e.g., via PACE authentication or basic password verification).

Note: This annex describes exemplary approaches for CSP support in authentication and authorisation. The actual implementation depends on the CSP type and its specifications, as defined in the corresponding CSP Protection Profile (CSP PP), and may vary across different CSP types.

The USE right applies generally to CSP security operations and does not specify the exact CSP service an asset is used for. This is intentional, as assets within the CSP are typically pre-configured for a specific purpose and a dedicated algorithm, resulting in a one-to-one relationship between the asset and the CSP service. Consequently, service-specific access rights are usually not required.

If an OCE sends a request to the application, and the application attempts to invoke a CSP service, the CSP will deny the request unless authentication has been completed.

To authenticate, the OCE initiates the process by sending messages based on a supported authentication protocol (e.g., PACE). The authorised application (see ACR) decrypts the request using the CSP unwrap operation, processes it, and invokes the necessary CSP services. After processing, it re-encrypts the response using the CSP wrap operation and returns it to the OCE.

PLATFORM DEPENDENCIES

A CSP serves as an abstraction layer that standardises cryptographic operations through a unified API, to provide secure CSP services.

Instead of implementing custom security functionalities, the CSP can rely on security mechanisms provided by the underlying platform. This is acceptable since the CSP undergoes a composite AVA_VAN.5 evaluation, which includes the operating system and hardware, as mandated by the requirements for the CSP PP (see AAnnex 1: Requirements for CSPs).

For example, the GlobalPlatform-CSP, as specified in [GP-AMD-N], relies on security functionalities from the SE platform, which are evaluated under [GP-SE-PP]. These include Card Management, Secure Communication, Privilege Management, Life Cycle Management, ELF Loading, Data Loading and Key Loading. By leveraging these evaluated platform functionalities, the CSP can:

- • Remotely create new Security Domains (SDs) dedicated for the application’s use case.

- • Assign privileges to these SDs, granting control to the CSP administrator, who acts on behalf of the application developer.

- • Change the access keys for the newly created SDs, ensuring that only the CSP administrator has access while the SE administrator no longer retains knowledge of these keys.

- • Create a new CSP instance associated with one of the newly created SDs.

- • Configure the CSP instance according to the application’s requirements.

- • Securely import sensitive resource values into the CSP instance, such as passwords and private or symmetric keys.

- • Load and install the application within one of the new SDs.

- • Ensure transport-layer encryption (e.g., SCP03 or SCP11) is applied to all these operations.

Security functionalities from the Java Card operating system, evaluated under [JC-PP], include Application Post-Issuance, Firewall, Sharable Interfaces, Global Arrays, Sensitive Array and Sensitive Result. These functionalities support the CSP by enabling:

- • Hosting the CSP instance within the Java Card environment.

- • Hosting the application instance alongside the CSP.

- • Enabling the CSP to verify whether an application is authorised to utilise CSP services.

- • Ensuring integrity checks on CSP service results.

- • Validating the integrity of parameters passed to CSP services.

By relying on evaluated platform security functionalities, the CSP simplifies its implementation, being able to focus on exposing a harmonised, secure API for cryptographic service. This reduces the need for custom security development while ensuring a standardised and secure interface for applications.

## G ANNEX 7: SAMPLE CSP WITHIN eUICC

An eUICC (embedded Universal Integrated Circuit Card) is a specialised type of SE designed specifically for mobile network applications (Telco) and, with the Secured Applications for Mobile (SAM) standard, may support additional application scenarios such as eID or payment.

To ensure isolation between different Mobile Network Operators (MNOs) and Application Service Providers (ASPs), the eUICC provides multiple levels of logically separated secure areas, ensuring independent operation, deployment, isolation and security enforcement. These include:

- • Logical Secure Elements (LSEs): Extend isolation beyond SDs by creating separate logical SE instances within a single physical SE. This enables multiple stakeholders, typically mobile operators, to coexist securely with independent security policies and key management.

- • Security Domain (SD): A dedicated secure space within an SE that manages application installations, enforces security policies and controls access to the applications it contains.

- • SAM SD: Builds on LSEs by extending their security model beyond telecommunications to applications such as payments and eID solutions. While LSEs separate stakeholders, SAM SDs enforce stricter cryptographic controls and management functionalities.

The GlobalPlatform-conform CSP, as specified in [GP-AMD-N], is designed to support both Telco and SAM use cases. The CSP Executable Load File (ELF), which is the binary of the CSP implementation, can be stored on the eUICC platform layer as part of the operating system, as shown in Figure 11. Alternatively, a separate CSP ELF may exist within each LSE. In either case, the CSP ELF enables the instantiation of new CSP instances in dedicated sub-SDs within both MNO-SD and SAM-SD, allowing different service providers to operate across LSEs.
