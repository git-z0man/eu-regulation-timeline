## 1. Introduction

<a id="sec-1-1"></a>
### 1.1 Introduction

Modern software products contain hundreds or thousands of components, each potentially harbouring vulnerabilities that threaten application and operating system security. Without component visibility, organisations operate blindly, discovering exposures only after exploitation occurs.

The Software Bill of Materials (SBOM) supports proactive vulnerability tracking by identifying components with potential vulnerabilities, allowing security teams to correlate component inventories against publicly disclosed security vulnerabilities and respond to emerging risks. Beyond immediate vulnerabilities, SBOM data supports the assessment of component viability and supply chain sustainability risks.

An SBOM is a formal record containing details and supply chain relationships of components included in the software elements of a product with digital elements. The SBOM should be drawn in a commonly used and machine-readable format identifying and documenting components contained in the products with digital elements. It can provide those who manufacture, purchase, and operate software with information that enhances their understanding of the supply chain, which has multiple benefits, in particular it helps manufacturers and users to track known newly emerged vulnerabilities and cybersecurity risks ^(1).

Core Capabilities • Transparency. Reveals third-party and open-source components comprising modern software.

- • Traceability. Links deployed software to upstream suppliers and downstream consumers.

- • Compliance. Provides auditable records for regulatory and contractual requirements.

- • Security. Supports vulnerability detection and software provenance verification.

SBOMs form a foundational data layer rather than a complete security solution. Their value emerges through integration with security processes such as timely patching, mitigation activities, and documented vulnerability handling decisions, with continuous maintenance, and systematic deployment across the software development lifecycle (SDLC).

This document provides practical guidance on the adoption of SBOM, and it is intended for organizations especially micro-, small and medium enterprises (SMEs) and stewards seeking to set up the initial capabilities to enhance the software supply chain transparency. It aligns with the security principles from the ENISA Secure by Design and Default Playbook ^(2), particularly supply chain controls, lifecycle management, and secure coding and verification practices. It introduces key concepts, industry standards, use cases and implementation practices to support organisations initiating their SBOM journey. In particular, this document:

- • outlines the SBOM implementation architecture and data flows based on a defined lifecycle;

- • presents an indicative SBOM threat model along with targeted risks;

- • lists measures to address the security issues across the SBOM ecosystem.

This technical advisory considers regulatory requirements such as those set out in the Cyber Resilience Act (CRA) ^(3), in particular essential requirements related to SBOM obligations for manufacturers but essentially describes recommended best practices that may go beyond those requirements.

It aims to provide technical context to such requirements by describing common threats across the SBOM lifecycle along with practical recommendations to mitigate them. However, this document should not be considered as a legal interpretation of the CRA.

<a id="sec-1-2"></a>
### 1.2 Scope and Context

This technical advisory is intended for guidance purposes only. The recommendations and best practices described herein are non-mandatory and do not create or modify any legal, regulatory, or compliance obligations.

The scope of this technical advisory is limited to Software Bill of Materials and does not cover other emerging Bill of Materials (BOM), such as Software Bill of Materials for AI, Hardware Bill of Materials (HBOM), Cryptographic Bill of Materials (CBOM) or other variants. While all artifacts may share some common principles, they also have differentiators and therefore are considered out of scope for this advisory.

This technical advisory remains sector-agnostic and applicable across all types of organisations regardless of their operational environment or industry. It is primarily focused on organisations that are at the early stage of SBOM adoption, and it does not provide a framework for assessing and improving organisational maturity. Future editions may cover the topic more extensively.

## 2. SBOM Architecture and Data Flows

<a id="sec-2-1"></a>
### 2.1 How Software Bill of Materials works

An SBOM is a structured inventory that captures software components and their dependencies for a given software product. Creating this "list of ingredients” gives manufacturers and users a better understanding and greater visibility into the “ingredients” of their software product, who produced them, where they came from and whether those “ingredients” may pose any risks.

The SBOM generators gather information from different sources in order to effectively identify firstparty components, open-source libraries, third-party commercial libraries, operating system packages, container images etc. Indicative sources of information are:

- • source code repositories,

- • build artifacts,

- • package manager manifests,

- • lock files,

- • container images,

- • binary analysis.

For each of the identified software components, the SBOM generator then collects and corelates metadata such as component name, component version, component creator, unique identifiers, license information, external references and dependencies. The scope and completeness of the collected metadata depend on its availability, the SBOM generator’s analysis methods, and the selected SBOM data model (e.g. CycloneDX or Software Package Data Exchange (SPDX)). The result is not merely a list of components but also a representation of their dependency relationships.

Upon the completion of the software composition analysis, the metadata collection and relationship discovery, an SBOM is generated in a standard machine-readable format, most commonly CycloneDX or SPDX. The SBOM can be generated and stored as JSON, XML, YAML or Tag-Value. It is important to highlight that SBOMs can be generated in different phases of the Software Development Lifecycle (SDLC). SBOMs generated in different SDLC phases serve different needs and contain different information.

The generation of an SBOM provides limited value unless it is actively consumed to support operational and security processes. The benefit of an SBOM lies in its integration into use cases such as vulnerability management, software asset inventory, license compliance, procurement, and regulatory compliance.

The need to treat an SBOM as more than a compliance artifact, is also reflected in the findings of the ENISA SBOM Adoption State of Play 2026, as respondents identified industry consensus on best practices for integrating SBOM production and consumption into software development practices as the highest priority (23%), followed by best practices for integrating SBOMs into risk and compliance processes (19%) and guidance on how SBOM production and consumption methods should evolve over time (19%). These findings highlight that organisations consider the operational integration of SBOMs into existing development, security, and governance workflows as a crucial step for a mature SBOM adoption.

Having established the key concepts of the SBOM data models, formats and types, this section presents the SBOM lifecycle and architecture. The SBOM provides added value when it is continuously managed throughout the SDLC and follows the software’s evolvement while components are added, updated, altered or deleted through new software releases.

A structured and automated SBOM lifecycle aims at ensuring that SBOMs are properly produced and consumed internally and externally. To highlight the need for this notion, a big gap was identified in the ENISA SBOM Adoption State of Play 2026, between what organisations need from SBOMs and what they actually receive. While 36 % of respondents stated that their organisations need all primary components and direct dependencies with declared known unknowns, only 29 % actually receive them. Furthermore, 24 % need SBOMs with full depth analysis, but only 14 % receive them. Finally, 27 % require SBOMs with depth analysis including declared known unknows, yet only 12 % receive them.

This section presents the SBOM lifecycle from both a conceptual and a technical perspective.. It starts by illustrating the SBOM life-cycle phases from generation to consumption and continuous maintenance, then presents how these phases can be integrated and automated into a CI/CD pipeline and finally lists the available open-source tool stack to support all defined phases.

#### 2.2.1 SBOM Lifecycle Phases

Figure 1 depicts the conceptual perspective of the SBOM lifecycle aligned with the key principles of SBOM. The lifecycle begins with the software build and SBOM generation based on the necessary sources of information, progresses to the SBOM validation to assess the quality of the generated SBOM, followed by cryptographic signing to protect its integrity and authenticity, secure storage, operational consumption and continuous maintenance and updates.

Figure 1 - SBOM Lifecycle 2.2.2 SBOM as part of a CI/CD Pipeline

The integration of SBOM generation and consumption into CI/CD pipelines is increasingly adopted and recognised as one of the best practises to achieve completeness, accuracy and trustworthiness. Automation enables organisations to generate, validate, update and consume up-to-date SBOMs. The findings of the SBOM Adoption State of Play 2026 reflect this, as 41 % of the organisations reported that they aim to fully automate SBOM generation for each release/build. However, automation is still a work in progress after the built stage as only 26 % of respondents believe that their organisations will fully automate SBOM updates across the product support period and almost 23 % believe that their organisations will partially automate this process.

While the previous section presented the conceptual perspective of the SBOM lifecycle, this section presents the technical implementation of SBOM as part of a CI/CD pipeline. The architectural diagram in Figure 2 aligned with the defined SBOM lifecycle phases depicts the integration of SBOM into the SDLC and the automation of each phase.

Each phase includes the key elements and processes to be considered successful along with basic failure points. This should not be interpreted as an exhaustive list of steps and aspects to consider when generating and consuming SBOMs but rather as an example of how SBOM integration and automation could be implemented.

The process begins with the source code build which produces the sources of information and then triggers the generation of SBOM. The SBOM generators attempt to identify the software components, extract relevant metadata, analyse dependencies, and produce machine-readable SBOMs in a standardized format (e.g., SPDX or CycloneDX). The generator collects, correlates, and structures metadata from the software build process and associated repositories.

Upon the successful generation of the SBOM, the validation process is triggered to assess if the SBOM is syntactically correct, conforms to the selected SBOM specification and contains the required metadata before triggering the next process. It is essential to also validate the component identifiers during this process.

Once validated, the SBOM is cryptographically signed to ensure authenticity and integrity before being stored in a repository or registry, to be consumed by downstream security tools.

The SBOM maintenance and update phase depicts the continuous process of keeping the SBOM up-to-date and synchronised with the current version of the software. Indicative automatic triggers are included to reflect the need to re-generate SBOMs and follow the lifecycle phases.

Finally, indicative security controls and trust mechanisms are depicted to protect the integrity, authenticity, and availability of SBOMs throughout the pipeline, enabling organisations to produce reliable SBOMs that can be consumed across development, security, operations, procurement and compliance teams.

## 4. SBOM Best Practices

This section presents indicative best practices for secure SBOM integration and automation based on the defined SBOM lifecycle while also complementing the suggested mitigation activities for the identified threats and general risks presented in the previous section.

<a id="sec-4-1"></a>
### 4.1 SBOM Integration and Automation

For a minimum viable implementation, begin with build-time integration as the foundation. This approach captures dependencies when they are most accurately known and requires minimal infrastructure changes.

Leverage existing continuous integration infrastructure by adding SBOM generation as a pipeline stage. Utilise command-line interfaces compatible with current build environments and store generated SBOMs alongside build artifacts using existing artifact repositories. Finally, implement validation through standard pipeline testing mechanisms. (Figure 3)

Figure 3 - Pipeline Integration

<a id="sec-4-1-1"></a>
#### 4.1.1 Integration Patterns

Build-Time Integration Pattern

Integrate generation immediately following successful compilation. Capture both direct and transitive dependencies while build context remains available. Generate supplementary metadata including build environment details and compilation parameters. Many build environments such as Yocto, Kubernetes, Linux, Zephyr, etc. have automatic SBOM generation capabilities already integrated, and the build just needs to enable them.

Event-Triggered Generation Pattern

Configure repository webhooks to initiate generation upon specific events. Support multiple trigger types including commit or pull request, and release events. Implement queuing mechanisms to handle concurrent generation requests. Maintain generation history for audit and rollback capabilities.

<a id="sec-4-1-2"></a>
#### 4.1.2 Common Configuration Requirements

Repository Structure Organisation

Establish a dedicated directory for SBOM storage within the repository structure. Maintain separation between source SBOMs and generated outputs. Implement naming conventions correlating SBOMs with their associated components and configure ignore patterns preventing SBOM inclusion in builds.

Pipeline Orchestration Templates

Define reusable pipeline segments for SBOM operations. Parameterise templates supporting multiple project types. Include standard validation and implement error handling and retry logic to manage transient failures.

Validation Checkpoints

Enforce format validation before artifact publication. Verify licence compatibility against organisational policies. Validate cryptographic signatures when attestation is required.

Vulnerability Management

Check for known vulnerabilities using configured vulnerability databases. Vulnerabilities identified through SBOM consumption should be linked to defined remediation timelines, severity thresholds and escalation paths. The remediation timelines should consider severity, exploitability, exposure, product criticality, availability of patches and compensating controls.

Automation Benefits

Automation eliminates manual generation inconsistencies whilst ensuring every build produces corresponding SBOM documentation. This continuous generation enables immediate vulnerability assessment when new threats emerge, while historical SBOM retention supports forensic analysis and compliance demonstration. Finally, automated validation prevents noncompliant SBOMs from entering production environments.

Prerequisites for Success

Successful integration requires mature continuous integration infrastructure and standardised build processes. Clear policies regarding generation triggers, storage locations, and retention periods must be established, while monitoring capabilities should track generation success rates and identify systematic failures.

SBOM processes should generate evidence for internal audits, conformity assessments, incident response and supervisory requests. This evidence includes generation logs, validation results, signatures, timestamps, release links and retention records.

Finally, organisations should document known gaps, exceptions and “known unknowns” in SBOM coverage, especially where some dependencies cannot be identified, supplier information is unavailable, or binary-only components cannot be fully analysed.
